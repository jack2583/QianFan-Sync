# 批量发布「自动定时」功能需求文档

> 版本：v1.0
> 状态：**需求已确认，进入开发阶段**
> 涉及页面：视频发布页（`/publish-center`）批量发布流程
> 调研依据：前端 `PublishCenter.vue` / `VideoBatchConfirmDialog.vue` / `useBatchSetApply.js` / `v2.js`；后端 `ext_api/__init__.py` / `ext_api/task_queue.py` / `init_db.py`

---

## 一、需求背景与目标

### 1.1 背景
当前视频批量发布支持「立即发布」和「每视频间隔 N 分钟」的相对间隔发布，也支持在每个账号/渠道上单独填写 `scheduleTime`（平台网页定时）。但缺少一种**统一、可预测的自动排程**能力：用户希望能一次性给整批视频设定一个起始时间，系统按固定规则自动为每个视频、每个平台铺开精确的发布时间，并自动填好各平台的定时字段，省去逐个手填。

### 1.2 目标
在点击「批量发布」弹出的确认框中，增加一个「自动定时」开关及相关参数。勾选后，系统按用户设定的起始时间与间隔规则，为**每一个「视频 × 平台」组合**计算出精确发布时间，并**自动填入该账号/渠道的 `scheduleTime`**。随后沿用现有批量发布流程：浏览器自动化登录各平台、在发布表单中带入该定时时间并提交，由平台在设定时刻发布。

> 关键语义：本功能 = `scheduleTime` 的**自动批量计算与填充**，不是新的定时执行机制。系统不在后端等待到点，也不改变"提交后浏览器立即跑完发布流程"的现有模式。

### 1.3 典型场景
运营者希望一批视频从次日上午开始，按整点依次发布到多个平台，且同一视频在不同平台错峰发布，避免同一时间集中发布带来的风控与内容挤占。

## 二、术语定义

| 术语 | 含义 |
|---|---|
| 视频（批次） | 队列中的一个视频，对应后端一条 `publish_batches` 记录 |
| 平台 / 账号 | 一个视频要发布到的目标账号，对应后端一条 `publish_details` 记录；一个视频可有多个账号（如抖音号A、快手号B） |
| 起始时间 | 整批任务中第一个视频的第一个平台的定时时间（T0） |
| 视频间隔 | 相邻两个视频**起始时刻**之间的分钟数（V） |
| 平台间隔 | 同一视频内，相邻两个平台定时时刻之间的分钟数（P） |
| 发布时间窗 | 允许设置定时的时间范围，本需求为每天 06:00:00 ~ 22:00:00 |
| `scheduleTime` | 平台网页「定时发布」字段；发布时由浏览器自动化填入，值非空则 `enableTimer` 派生为 true |

## 三、用户操作流程（交互需求）

### 3.1 入口
在视频发布页点击「批量发布」→ 打开「批量发布确认」弹窗（`VideoBatchConfirmDialog.vue`）。

### 3.2 新增控件（位于发布间隔设置区附近）
1. **「自动定时」勾选框**（默认不勾选）
   - 未勾选：保持现有行为（立即发布 / 发布间隔，默认 30 分钟），不显示下列参数。
   - 勾选：展开定时参数区。原有的「发布间隔（intervalMinutes，默认 30 分钟）」**始终保留并显示**，它控制的是浏览器自动化的**操作间隔**，与平台定时时刻互不影响；提交时照常传用户输入值，不再强制为 0，避免连续操作触发平台风控。
2. **起始发布时间**（日期时间选择器）
   - 格式：`YYYY-MM-DD HH:mm:ss`，如 `2026-11-27 10:00:00`。
   - 默认：当前时间向后取整到下一个整点（如当前 21:40 → 默认 22:00；若已过 22:00 → 次日 06:00）。
   - 校验：必须在发布时间窗内（06:00:00 ≤ 时刻 ≤ 22:00:00）且晚于当前时间。
3. **不同视频间隔时间**（数字输入，单位分钟）
   - 默认值：`60`。
   - 范围：建议 1 ~ 1440，步长 1。
4. **同一视频不同平台间隔时间**（数字输入，单位分钟）
   - 默认值：`15`。
   - 范围：建议 1 ~ 240，步长 1。

### 3.3 提交前预览
勾选自动定时后，在弹窗内提供一个「排程预览」列表，展示前 8 条计算出的定时时刻，格式如：

```
视频1 · 抖音(账号A)   2026-11-27 10:00:00
视频1 · 快手(账号B)   2026-11-27 10:15:00
视频2 · 抖音(账号A)   2026-11-27 11:00:00
视频2 · 快手(账号B)   2026-11-27 11:15:00
...
```

让用户提交前即可核对排程结果。预览内容与最终写入的 `scheduleTime` 必须完全一致。

### 3.4 提交
确认后随批量发布请求一并提交，新增字段：
```json
{
  "videos": [ ... ],
  "auto_schedule": {
    "enabled": true,
    "start_at": "2026-11-27 10:00:00",
    "video_interval_minutes": 60,
    "platform_interval_minutes": 15
  }
}
```
> 计算与填充在前端完成（见 5.1），`auto_schedule` 随请求传给后端仅用于记录/展示；后端发布链路无需感知该字段即可正常工作。

## 四、排程计算规则（核心）

### 4.1 排序规则

| 规则 | 内容 |
|---|---|
| R1 视频顺序 | 按确认弹窗中勾选的视频在队列中的先后顺序（索引升序），即 `selectedIndexes.sort()` 后的顺序 |
| R2 平台顺序 | 每个视频内，按 `publishAccountIds` 数组顺序（用户勾选账号的顺序） |

### 4.2 计算公式

设：
- `T0` = 起始时间
- `V` = 视频间隔（分钟）
- `P` = 平台间隔（分钟）
- 第 `i` 个视频（`i` 从 0 开始），其第 `j` 个平台（`j` 从 0 开始）

基础公式：

```
T(i, j) = T0 + i × V + j × P
```

「6 7 9」为「6 7 8 9」笔误，按上述等间隔序列实现。

### 4.3 重叠顺延规则

| 规则 | 内容 |
|---|---|
| R3 同视频内 | 计算每个时刻后，若 `T(i,j) < T(i,j-1)`，则令 `T(i,j) = T(i,j-1)` |
| R4 跨视频 | `T(i,0)` 不得早于 `T(i-1, 最后)`，否则顺延到该时刻 |
| R5 后续排程 | 顺延后，后续任务从顺延后的时刻继续按 4.2 公式排布 |

示例：V=60、P=15、每视频 5 个平台时，视频1最后一个平台为 11:00，视频2第一个平台基础值为 11:00，不早于前者，无需顺延；若算出早于 11:00，则顺延到 11:00。

### 4.4 时间窗规则

| 规则 | 内容 |
|---|---|
| R6 窗口范围 | 所有定时时刻必须落在每天 06:00:00 ~ 22:00:00 内 |
| R7 越界处理 | 任一时刻早于 06:00:00 或晚于 22:00:00，**禁止提交** |
| R8 提示内容 | 明确列出越界的视频序号、平台名称、越界时刻与原因 |
| R9 无副作用 | 校验不通过时不写入任何定时；用户调整起始时间、间隔或减少视频数后重试 |

不采用顺延次日 06:00 的方案；超出窗口的任务也不静默跳过，而是整体不提交。

### 4.5 平台约束校验规则

| 规则 | 内容 |
|---|---|
| R10 约束来源 | 按目标平台的 `scheduleTime` 自身约束校验（见 `platforms.js` 各平台 `scheduleTime` 字段的 `placeholder`，如微信"最近 7 天，需大于当前 1 小时"、抖音"7 天内，5 分钟间隔"） |
| R11 校验方式 | 计算出的时刻若不满足该平台限制，禁止提交 |
| R12 提示内容 | 明确提示具体平台与原因 |

### 4.6 排程示例（T0=10:00:00，V=60，P=15，每视频 2 个平台）

| 视频 | 平台 | 计算 | 填入的 scheduleTime |
|---|---|---|---|
| 视频1 | 抖音 | 10:00 + 0×60 + 0×15 | 2026-11-27 10:00:00 |
| 视频1 | 快手 | 10:00 + 0×60 + 1×15 | 2026-11-27 10:15:00 |
| 视频2 | 抖音 | 10:00 + 1×60 + 0×15 | 2026-11-27 11:00:00 |
| 视频2 | 快手 | 10:00 + 1×60 + 1×15 | 2026-11-27 11:15:00 |
| 视频3 | 抖音 | 10:00 + 2×60 + 0×15 | 2026-11-27 12:00:00 |

### 4.7 与现有定时字段的关系

现有 `scheduleTime` 就是**平台网页上的「定时发布」字段**：任务运行时，浏览器自动化登录各平台，把时间填入该字段并提交，由**平台自身**在设定时刻真正发布。`enableTimer` 由 `scheduleTime` 是否非空派生（前端构造 `publishData` 时 `enableTimer = scheduleTime ? 1 : 0`，图片侧由各 panel 用 `!!scheduleTime` 派生）。

本功能的「自动定时」**不是另一套定时机制**，也不在后端排队等待到点。它就是**批量计算每个「视频 × 平台」的 `scheduleTime`，并自动填入对应账号/渠道的该字段**，替代用户逐个手动填写。

由此得出：

| 规则 | 内容 |
|---|---|
| R13 同一字段 | 两者是同一个字段，不存在"互斥/双重定时"问题；本功能只是 `scheduleTime` 的自动批量填充器 |
| R14 覆盖原值 | 勾选自动定时时，计算出的时刻覆盖这些账号/渠道原有的 `scheduleTime`（无论原来是否手填过）；未参与本次排程的账号不受影响 |
| R15 未勾选行为 | 未勾选时行为完全不变：沿用用户各平台手填的 `scheduleTime`，或立即发布 |
| R16 enableTimer | 无需用户单独设置，仍按 `scheduleTime` 非空自动派生 |

可行性说明：发布由平台定时负责，因此浏览器自动化只需在各自定时时刻之前把任务提交掉即可，不必挂机等到点（即使最后一个视频排在次日，也可当天提交并填好定时）。

## 五、技术方案

### 5.1 前端改动（主要工作量）

| 文件 | 改动 |
|---|---|
| `frontend/src/components/VideoBatchConfirmDialog.vue` | 增加「自动定时」开关、三个参数控件、排程预览列表（前 8 条）；时间窗越界与平台约束校验不通过时禁用提交并提示；`emit('confirm')` 携带 `auto_schedule` |
| `frontend/src/utils/autoSchedule.js`（新增） | 排程计算与校验纯函数：按 4.2 公式计算 + 重叠顺延 + 时间窗校验 + 平台约束校验 + 生成预览数据 |
| `frontend/src/views/PublishCenter.vue` | `confirmBatchPublish` 接收 `auto_schedule`，计算后为每个选中视频的每个 `publishAccountId` 写入该视频快照的 `accountOverrides[aid].scheduleTime`（覆盖原值）；`intervalMinutes`（操作间隔，默认 30 分钟）照常透传；`auto_schedule` 透传给 API |
| `frontend/src/api/v2.js` | `batchPublishVideos(videos, intervalMinutes, autoSchedule)` 增加第三个参数，POST body 带 `auto_schedule` |

计算与填充放在前端。写入的是**每个视频快照的账号级 `scheduleTime`**。现有 `mergeConfig` / `_resolveScheduleTime` 会按「账号级 > 渠道级 > 平台默认」优先级解析，账号级写入即生效；`enableTimer` 随即由 `scheduleTime` 非空派生，无需额外改动。

### 5.2 后端改动（最小或无需）

| 文件 | 改动 |
|---|---|
| `backend/ext_api/__init__.py` | `videos_batch_publish` 接收并记录 `auto_schedule`（可选，便于发布历史/任务 payload 追溯）；发布链路本身无需改动——`payload['scheduleTime']` 已有完整的 `enableTimer` / `schedule_time_str` 解析与填入平台的实现 |

不需要新增 `publish_details.scheduled_at` 列、改造 `_scheduler_tick` 按时刻入队、或在自动定时时跳过相对间隔链。因为发布时刻由平台网页定时承担，后端任务仍按现有方式尽快入队执行，不需要精确到点的队列调度。

### 5.3 关键实现约束

| 规则 | 内容 |
|---|---|
| R17 串行模型 | `TaskQueue(max_concurrent=1)` 保持不变，避免并发风控 |
| R18 发布间隔（操作间隔） | 无论是否启用自动定时，`intervalMinutes` 始终使用用户输入值（默认 30 分钟），照常传给后端控制视频间的操作节奏，避免连续操作触发平台风控；平台实际发布时刻仍完全由 `scheduleTime` 决定 |
| R19 平台限制 | 各平台定时字段的格式与限制不同，计算出的时间需满足目标平台约束，前端做二次校验与拦截 |
| R20 重启影响 | 现有「服务重启后 pending 任务会丢失并标记 failed」的限制对自动定时同样适用，但因任务在提交后即尽快执行、不挂机等待，实际影响很小；不需要单独的重启恢复设计 |

## 六、验收标准
1. 未勾选自动定时时，现有批量发布行为完全不变（回归）。
2. 勾选后，三个参数可编辑、有默认值、有范围与格式校验。
3. 按公式计算的每个「视频×平台」时刻正确，重叠时按 R3~R5 顺延规则处理。
4. 任一时刻越界（<06:00 或 >22:00）或不满足平台约束时，提交被拦截、明确提示原因，且不写入任何定时。
5. 提交后，每个「视频×平台」的正确时刻被写入对应账号/渠道的 `scheduleTime`；在任务 payload / 发布历史详情中可核验该值。
6. 发布时各平台发布表单正确带入该定时时间（`enableTimer` 随之派生为 true），平台显示为预约发布而非立即发布。
7. 排程预览列表（前 8 条）与最终写入的 `scheduleTime` 完全一致。
